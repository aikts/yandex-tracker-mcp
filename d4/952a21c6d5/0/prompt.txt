Найденные проблемы

1. Коллизия имён в fields — падение с сырым Python-исключением. Ключ в fields, совпадающий с именем выделенного параметра, ломает вызов:

issue_update(fields={"parent": null})
→ TrackerClient.issue_update() got multiple values for keyword argument 'parent'

Воспроизводится и на issue_create (fields={"assignee": ...}). Наружу течёт внутреннее имя модуля. Нужно либо мержить fields с выделенными параметрами, либо валидировать пересечение с понятной ошибкой.

2. Нет способа очистить assignee и parent. None в схеме означает «не передавать», assignee="" даёт 422, а обходной путь через fields заблокирован проблемой №1. Для deadline и storyPoints очистка работает (fields: {deadline: null}), для выделенных параметров — нет.

3. get_priorities не отдаёт id. Возвращаются version/key/name/order, при этом обе схемы (IssuePriorityRef.id) и докстринги ссылаются на этот инструмент как на источник id. Для сравнения, get_issue_types id отдаёт. Плюс список глобальный: minimal и important в AP недопустимы, узнаётся это только по 422 при создании.

4. IssueTypeRef / IssuePriorityRef / IssueParentRef пропускают пустой объект. type={} проходит клиентскую валидацию и приводит к невнятному 400 Incorrect data format от Трекера. У IssueComponentRef валидатор «ровно одно из id/name» есть — стоит добавить «хотя бы одно» и остальным.

5. Противоречивый объект резолвится молча. type={"id":"1","key":"task"} → выставился bug: побеждает id, key игнорируется без предупреждения. Поведение стоит либо задокументировать, либо запретить.

6. Стык шаблонов и issue_create неполный. Описание issue_create предписывает копировать значения fieldTemplates в параметры, но assignee шаблон отдаёт объектом пользователя, а параметр принимает только строку/число — прямое копирование падает на валидации. followers при этом объект принимает. Плюс макросы в шаблонах не разворачиваются: summary: "Релиз {{today}}" создал задачу с литеральным {{today}} (AP-141). Оба момента стоит проговорить в докстринге.

7. Мелочь в именовании. На вход storyPoints, на выход story_points; аналогично createdAt/created_at. При обратной подстановке ответа в апдейт это ловушка.

8. queue_get_fields для AP не вернул ни parent, ни estimation/originalEstimation, хотя parent через API выставляется, а originalEstimation виден в выдаче issues_find по AP-124. Список редактируемых полей неполный, а докстринг fields называет его обязательным источником истины перед созданием.
